# GitHub 定时调度排查

本项目每天北京时间 09:30、15:30 尝试运行。第二次会先查服务器状态，已经领取时跳过。两个时间共用 GitHub 调度服务，无法保证独立补偿。

## 分清三类故障

| 现象 | 含义 | 下一步 |
|---|---|---|
| Actions 完全没有该时段的新记录 | 未创建可见的运行；不是领取脚本执行失败 | 查默认分支、工作流启用状态、调度记录和 GitHub 状态；不要改密码 |
| 有 schedule 记录，配置检查失败 | 定时开关缺失或值不合法 | Repository Variables 设置 MAJSOUL_AUTO_ENABLED=true；false 是主动暂停 |
| 有记录，登录／版本／领取步骤失败 | 定时已经触发，故障发生在执行阶段 | 根据失败步骤和脱敏错误码排查 |

## 已检查到的事实（2026-11-11）

原仓库默认分支 main，工作流位于默认分支，state 为 active，cron 的 UTC 换算正确，仓库未归档且近期有提交。2026-11-11 10:05:52 北京时间的手动运行成功；当天上午的 schedule 记录在检查时仍未出现。此前 2026-11-10 有 schedule 记录，但领取 job 被定时条件跳过。

这些证据说明手动执行可用，不能证明具体哪一次调度是在排队还是被丢弃。GitHub 的公开接口不提供该次未投递事件的内部日志。GitHub 状态页正常也不能排除单仓库问题。

## 官方规则与可行处理

1. 工作流必须存在于默认分支，并处于启用状态。公开仓库 60 天无活动可能被停用。本仓库近期活跃，因此此次不符合长期无活动这一条件。
2. 官方明确说明 schedule 可能在负载高时延迟，部分排队任务可能被丢弃。避开整点可降低部分高峰影响，不能保证准时；本项目保留用户选择的半点。
3. 官方也说明：关联的 actor 账号被停用、删除或撤销配置时，定时可能停止，而手动运行仍正常。由有写权限的活跃用户修改并提交 cron 可以重新激活关联。当前没有证据证明本仓库的账号存在此问题。
4. 定时通知发给最后修改 cron 的用户。手动运行能收到邮件，不保证定时通知接收人一定相同。推荐仓库所有者检查自己的 Actions 邮件设置。

参考：[官方触发排错](https://docs.github.com/en/actions/how-tos/troubleshoot-workflows)、[schedule 规则与 actor](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)、[GitHub 状态页](https://www.githubstatus.com/)。

社区有“禁用后启用”或重新提交 cron 后恢复的报告，但并非官方承诺或本仓库已验证的根因。可在 Actions 工作流右上角菜单 Disable workflow 后 Enable workflow 一次，然后等待下一个完整时段。添加下午时段会实际修改并提交 cron；不应连续几分钟改一次，导致难以比较效果。

如怀疑 actor 关联，所有者可亲自在 GitHub 网页编辑 cron 为等价的 `30 1,7 * * 0-6`（每天 09:30、15:30，时间不变），提交到 main 后观察下一时段。这是官方所述重新关联方式的应用，不保证解决所有调度问题。

## 仍不触发时

若重新启用后，上午和下午的完整时段持续都没有 schedule 记录，向 GitHub Support 或 Community 提交以下非敏感信息：仓库链接、默认分支、工作流路径和 ID、当前 cron、修改提交、预计 UTC 时间、实际 schedule 记录列表，以及成功手动运行链接。不要上传 Secrets 或雀魂账号信息。需要仓库所有者自行提交，本项目不会自动对外发送反馈。

要绕开 GitHub 原生 cron，可使用独立云端定时器调用工作流的 workflow_dispatch API。需要额外服务账号以及仅授权目标仓库 Actions 写权限的凭据；该凭据应保存在外部调度器的密钥设置中。它能绕开原生 cron 事件投递问题，但仍依赖 GitHub Actions 执行服务。完全绕开 GitHub 则需要另一台持续运行的云端环境。

独立定时器、令牌和漏跑报警尚未配置。请勿把下午补跑、GitHub 邮件或未实施的外部调度描述为“保证不漏领”。
